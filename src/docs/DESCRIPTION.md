# Проект «CRM-платформа"

В этом проекте вам предстоит разработать простую и функциональную CRM-систему — Customer Relationship Management, то есть систему управления взаимоотношениями с клиентами. Она должна включать в себя управление клиентами, сделки и базовые отчёты по продажам.

## Подготовка

Прежде чем приступить к выполнению, ознакомьтесь с [макетом](https://www.figma.com/design/gBQd0mpKKDUqB7ubymaJIa/CRM%E2%80%93%D0%BF%D0%BB%D0%B0%D1%82%D1%84%D0%BE%D1%80%D0%BC%D0%B0) приложения и [шаблоном проекта](https://github.com/yandex-praktikum/higher-web-practice-crm).

Проект достаточно объёмный и состоит из множества страниц, но не стоит переживать: все страницы имеют общую структуру, и уже есть макет UI-кита.

Начинайте с создания UI-кита приложения.

В этом проекте нет специальных требований по использованию UI-библиотек, поэтому для начала определите, на чём будут основываться компоненты. Вы можете использовать:

- CSS, SCSS или TailwindCSS для стилизации, чтобы самостоятельно писать логику работы компонента.
- Headless-библиотеку, например Radix UI, Headless UI.
- Полноценную UI-библиотеку с поддержкой тем, например [Shadcn](https://ui.shadcn.com/), [Chakra UI](https://chakra-ui.com/), [Mantine UI](https://mantine.dev/), [Ant Design](https://ant.design/), [Bootstrap](https://react-bootstrap.github.io/)

Можете выбрать инструменты, которые вам хорошо знакомы, или попробовать что-то новое. Главное, чтобы они приносили пользу, а не доставляли лишних неудобств.

## Реализация

Сначала задайте базовые стили: сетку, отступы, цвета, типографику, затем приступайте к базовым компонентам: кнопкам, инпутам и чекбоксам. Уже из них вы сможете создать переиспользуемые компоненты.

Настройте [роутинг](https://reactrouter.com/) приложения, не забудьте про использование компонента [Outlet](https://reactrouter.com/api/components/Outlet) для вложенных роутов. Для тех страниц, которых пока нет, создайте компонент-заглушку.

Как только базовая вёрстка будет готова, приступайте к донастройке проекта. В качестве стейт-менеджера используйте [Redux Toolkit](https://redux-toolkit.js.org/). Это удобный и производительный инструмент для управления состоянием в React-приложениях. Он включает утилиты, которые упрощают работу с глобальным состоянием, иммутабельностью и асинхронными действиями.

Redux, Redux Toolkit и асинхронные экшены вам должны быть уже знакомы. В этом проекте вы будете использовать ещё один инструмент из семейства Redux Toolkit — [RTK Query](https://redux-toolkit.js.org/rtk-query/overview).

### Пример создания и использования API

```typescript
// @api/posts/index.ts
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

export const api = createApi({
  baseQuery: fetchBaseQuery({ baseUrl: 'https://api.example.com' }),
  endpoints: (builder) => ({
    // Query для получения списка постов
    getPosts: builder.query({
      query: () => '/posts',
    }),
    // Mutation для создания нового поста
    createPost: builder.mutation({
      query: (newPost) => ({
        url: '/posts',
        method: 'POST',
        body: newPost,
      }),
    }),
  }),
});

export const { useGetPostsQuery, useCreatePostMutation } = api;


// @features/posts-list/index.tsx
import { useGetPostsQuery, useCreatePostMutation } from '../store/api';

function PostsList() {
  const { data: posts, isLoading, error } = useGetPostsQuery();
  const [createPost, { isLoading: isCreating }] = useCreatePostMutation();

  const handleAddPost = async () => {
    await createPost({ title: 'Новый пост' }).unwrap();
  };

  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;

  return (
    <div>
      {posts.map(post => <Post key={post.id} post={post} />)}
      <button onClick={handleAddPost} disabled={isCreating}>
        Добавить
      </button>
    </div>
  );
}
```

#### Что такое Query и Mutation в RTK Query?

**Query** — это запрос на получение данных (аналог GET). Для каждого query RTK Query автоматически генерирует хук `use...Query`, который возвращает объект с полями `data`, `isLoading`, `error` и другими. Query-запросы кешируются по аргументам: если одни и те же данные запрашиваются повторно, они берутся из кэша без лишних вызовов API.

**Mutation** — это запрос на изменение данных (POST, PUT, PATCH, DELETE). Для каждой мутации генерируется хук `use...Mutation`, который возвращает кортеж [trigger-функция, объект с состоянием]. Мутации часто используются для создания, обновления или удаления записей и могут инвалидировать теги, чтобы автоматически обновить связанные Query-данные.

Для более сложных случаев добавляются теги (`providesTags` / `invalidatesTags`), параметры запроса, преобразование ответа и другие настройки.

В качестве бэкенда будет выступать заготовленный [json-server](https://github.com/typicode/json-server) с моковыми данными, самостоятельно писать бэкенд не нужно. Также в директории `src/types` будут лежать заготовленные типы по каждой сущности приложения.

Для запуска мокового сервера откройте окно терминала и выполните команду:

```bash
npm run server
```

## Рекомендации по формам: `react-hook-form` + `zod`

Для страниц с формами (клиенты, сделки, задачи, профиль) удобно использовать схему-валидацию:

- `react-hook-form` берёт на себя сбор значений формы, управление ошибками и обработку `onSubmit`.
- `zod` описывает контракт полей (тип, обязательность, форматы) в одном месте и позволяет централизованно задавать нормализацию.

Если выбираете эту связку, подключайте `zodResolver`, чтобы ошибки zod автоматически попадали в `react-hook-form`.

Практика, которую стоит выполнять:

- Делайте валидацию по схеме, а не «по месту» в обработчиках. Тогда ошибки предсказуемы и их легче тестировать.
- Для полей с текстом (например, комментарий) полезно нормализовать ввод на уровне схемы: `trim()` и удаление пробелов, чтобы в submit-пейлоад попадали чистые значения.
- В режиме edit используйте `defaultValues` / `reset`, чтобы форма заполнялась из initial-данных.
- Ошибки показывайте рядом с полем (под соответствующим инпутом), а обязательные поля помечайте звёздочкой в лейбле.

## Что нужно тестировать

1. **Функции-хелперы и утилиты.** Выделите в отдельные модули (папку `utils/` или `helpers/`) все вспомогательные функции, которые не зависят от React и Redux. Это могут быть: форматирование, преобразования, вычисления.

2. **Сложное или неочевидное поведение компонентов.** Не нужно тестировать каждый компонент на наличие текста или классов, это часто приводит к хрупким тестам. Сосредоточьтесь на компонентах, в которых есть:

- нетривиальная внутренняя логика (кастомный селект, дропдаун с фильтрацией);
- условный рендеринг, зависящий от пропсов или состояния;
- обработка пользовательского ввода с валидацией;
- взаимодействие с Redux (диспачи, селекторы).

3. **Основные сценарии работы приложения (опционально, но приветствуется).** Если останется время, напишите несколько интеграционных тестов, проверяющих сквозной сценарий: добавление товара в корзину, переход к оформлению, ввод данных и подтверждение заказа. Можно смокировать API через `jest.mock`.

Для тестирования компонентов используйте `React Testing Library` вместе с `Jest`. Имитируйте действия пользователя (клики, ввод текста) и проверяйте результат на странице, а не внутренние детали реализации. При использовании `React Testing Library` важно выбирать селекторы, максимально приближенные к тому, как пользователь взаимодействует с интерфейсом: `getByRole`, `getByText`, `getByLabelText`, `getByPlaceholderText`, `getByAltText`.

### Как мокать зависимости в компонентных тестах

- `IntersectionObserver`: в тестах для хуков или компонентов с наблюдением используйте мок, который вызывает callback с `isIntersecting: true`, и проверяйте очистку (disconnect / unobserve) при размонтировании.
- `RTK Query`: если компонент зависит от `use...Query` / `use...Mutation`, мокайте сами хуки (возвращайте нужные `data` / `isLoading` / `error`), чтобы тест фокусировался на UI-логике.
- Не пишите unit-тесты на стандартное поведение `Redux Toolkit` или `React Router` — проверяйте вашу связку: валидацию, сбор payload, условный рендеринг, обработчики.

## Чего не нужно делать

- Не стремитесь покрыть тестами каждую строчку кода, достаточно проверить логику.
- Избегайте тестирования тривиального рендера, например «компонент отображает заголовок», если этот заголовок статичен.
- Не пишите тесты на стандартное поведение библиотек (React Router, Redux Toolkit) — они уже протестированы авторами.

## Рекомендации по организации тестов

- Размещайте тесты рядом с тестируемыми модулями: `utils/formatPrice.ts` и `utils/formatPrice.test.ts`; `components/dropdown/dropdown.tsx` и `components/dropdown/dropdown.test.tsx`.
- Для redux-логики (редьюсеры, экшены) можно писать отдельные тесты, если она достаточно сложная. Для простых слайсов это не обязательно.

## Минимальная настройка Jest и Testing Library

Чтобы тесты работали «из коробки» в шаблоне проекта:

- В `package.json` должна быть команда запуска тестов, например `test": "jest"`.
- Окружение по умолчанию — `jest-environment-jsdom` (браузероподобные API в тестах).
- В файле настройки (например, `src/test/setupTests.ts`) один раз подключите `@testing-library/jest-dom/jest-globals`, чтобы были матчеры вроде `toBeInTheDocument`.
- Для импорта SVG и других статических ресурсов как модулей настройте заглушки (например, mock-компонент для `*.svg` и `*.svg?react`), иначе Jest может падать на неизвестных расширениях.

## Соответствие заданию: страницы и функционал

Для успешной сдачи проекта ваш сайт должен иметь такую функциональность.

### Перечень страниц

1. Начальная страница.
2. Страница регистрации (Registration).
3. Главная страница (Dashboard).
4. Страница клиентов (Clients).
5. Страница сделок (Deals).
6. Страница отчётов (Reports).
7. Страница задач (Tasks).
8. Страница профиля пользователя (User Profile).

### Функционал страниц

1. Начальная страница

- Общая информация о проекте — название, краткое описание (УТП).
- Форма авторизации:
  - `email`;
  - `пароль`;
  - кнопка «Войти» — при совпадении регистрационных данных происходит редирект на главную страницу;
  - кнопка «Регистрация» — переход на страницу «Регистрация».

2. Страница регистрации (Registration)

Форма регистрации:

- `email`;
- `пароль`;
- `имя`;
- кнопка «Зарегистрироваться» — проверяем, что e-mail уникален, валидность пароля.

Функционал раздела: если валидация проходит, то регистрируем пользователя.

3. Главная страница (Dashboard)

Отображение сводной информации и статистики:

- Количество клиентов: сегодня итого, добавилось сегодня, добавилось на этой неделе, добавилось в этом месяце, добавилось в этом квартале.
- Количество активных сделок: сегодня итого, добавилось сегодня, добавилось на этой неделе, добавилось в этом месяце.
- Количество завершённых сделок: сегодня итого, добавилось сегодня, добавилось на этой неделе, добавилось в этом месяце.
- 10 наиболее активных клиентов, которые участвуют в большинстве сделок текущего пользователя.
- Последние 10 активных сделок текущего пользователя.
- Последние 10 задач текущего пользователя.

Кнопки для быстрого доступа к разделам:

- Добавление клиента.
- Добавление сделки.
- Добавление задачи.

4. Страница клиентов (Clients)

Поля клиента: Имя, Телефон, Email, Название компании, Сайт, Дата добавления, Комментарий.

Список: содержит все поля клиента, возможность сортировки и фильтрации (поиска) по всем полям. При нажатии на строку открывается модальное окно редактирования.

Удаление: при удалении клиент помечается как удалённый. С таким клиентом нельзя добавить сделку, но сделки с ним отображаются.

5. Страница сделок (Deals)

Поля сделки: Название, Клиент, Описание, Сумма, Этап (статус), Дата создания, Дата завершения.

Статусы сделки: Новая, В работе, Завершена, Отменена.

Список: содержит все поля сделки, возможность сортировки и фильтрации (поиска) по всем полям. При нажатии на строку открывается модальное окно редактирования.

6. Страница отчётов (Reports)

Страница содержит несколько вкладок с отчётами.

- Общий отчёт по продажам: отображение всех завершённых сделок за период (неделя, месяц, квартал). Поля отчёта: ID сделки, Название, Клиент, Сумма, Дата завершения.
- Отчёт по этапам сделок: анализ сделок по текущим этапам (статусам). Поля отчёта: Этап сделки, Количество сделок на этапе, Общая сумма сделок на этапе.

Отчёты по клиентам:

- Отчёт по новым клиентам: количество новых клиентов за период (неделя, месяц, квартал). Поля отчёта: ID клиента, Имя клиента, Компания, Дата добавления.
- Отчёт по активности клиентов: информация о взаимодействии с клиентами (количество сделок, завершённые задачи). Поля отчёта: ID клиента, Имя клиента, Количество сделок, Завершённые задачи.

Отчёты по задачам:

- Отчёт по просроченным задачам: список задач, которые не были выполнены в срок. Поля отчёта: ID задачи, Название задачи, Ответственный, Дата срока выполнения, Статус.
- Отчёт должен быть представлен в формате стандартной таблицы с возможностью сортировки по каждому полю. Должна быть предусмотрена пагинация таблицы.

Фильтрация отчётов. Каждый отчёт должен иметь форму для фильтрации данных по датам, менеджерам, этапам сделок.

7. Страница задач (Tasks)

Поля задачи: Название, Сделка, Описание, Выполнить до, Исполнитель, Статус, Дата создания.

Статусы задачи: Новая, В работе.

8. Страница профиля пользователя (User Profile)

Форма настроек:

- `email`;
- `пароль`;
- `имя`.
